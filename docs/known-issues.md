# 已知问题（Known Issues）

## 已修复：skill_manager 误路由（2026-08-15 实机发现，0.5.3 修复）

**现象**：普通任务消息中含「技能」字样（如群通知文案『技能热插拔』）被路由到 skill_manager_tool，返回『😑未识别的技能管理命令』，主任务不执行。

**复现**：发送『发送润工作群通知：…技能热插拔…』→ skill_manager 报未识别命令，通知未发出。

**根因**：存在两个竞争路由。技能管理自然语言解析把任何包含「技能」的文本兜底为 `list`；实测 Chatflow 又在插件调用前用「sys.query 包含技能」直接分流到独立 `skill_manager` 节点，导致主工具完全没有机会纠正误判。

**修复**：0.5.3 将解析收口到 `core/skills/commands.py`。`my_claw` 仅在解析出查看、新增、删除、下载或依赖安装动作时短路到 `skill_manager`；其他输入继续主 agent 循环。`skill_manager` 自身复用同一解析器，不再以「技能」单词兜底。部署侧移除 Chatflow 的「包含技能」条件分支，所有输入统一进入 `my_claw`，消除第二路由源。

**回归验证**：覆盖普通业务消息「发送润工作群通知：技能热插拔功能演示中」、五类管理命令及「帮我看看技能列表」等语序变化；64 项单元测试与 Dify SDK 启动校验通过。公司 Dify 最终包实机 workflow run `094257d3-053c-48b3-852a-2b1a0bc0d7a1` 仅执行 `start → myclaw → ansMc` 且成功，指定消息进入主 agent 循环，不再返回技能管理命令错误；真正的「查看技能」命令仍能正常短路到管理器。
